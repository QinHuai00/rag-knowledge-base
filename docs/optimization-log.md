# rag-kb 优化实录：V1 → V4（离线实测）

这份文档记录的是**实际动手做过、跑出过数字**的优化，不是"计划要做"。
每一级都按固定结构写：**现象 → 原因分析 → 改法 → 代码位置 → 实测结果 → 踩坑**。
所有命令都在项目根目录（`rag-knowledge-base/`）下执行。

## 三条诚实约定（先读这个）

1. **离线数字 ≠ 真实模型指标**。默认无 API Key、无网络，跑的是「哈希向量 + 抽取式回答」的离线模式。
   离线数字只验证**工程链路正确、优化方向对**，不能当成真实语义检索效果。接 BGE + 大模型后必须用同一脚本重跑。
2. **不编数字**。本文所有数字都是真实跑出来的，日期、样本量、模式都写清楚了。没测的会标「未测（原因）」。
3. **一次只改一个变量**。消融实验的每一级只允许改一个东西，这样被问「哪个改动起的作用」才答得出来。

---

## 1. 基线画像

- 初版 V1：600 字固定块 + 纯向量召回，无父子块、无 BM25、无精排。
- 语料：`data/raw` 下 3 份虚构制度文档（员工手册、报销制度、IT 服务指南），V1 固定块切出 **34 块**；
  V4 父子块切分为 **48 个子块 / 34 个父块**。
- 基线测试：19 个 unittest 全绿；评测集 24 条，`source_recall@5 = 100%`（但这个指标太松，见 1.1）。

## 1.1 先把评测集做严（这是优化的地基）

**现象**：初版的 `source_recall@5` 恒为 100%，任何改动都不动——因为语料只有 3 份文档，随便召回 Top-5 都能覆盖「正确的那份文件」，这个指标**根本测不出优化有没有用**。

**原因分析**：指标粒度太粗。「召回对了哪份文件」在 3 份文档的小语料上天然满分；真正该问的是「召回对了哪一小节」，制度类文档一个文件里有十几个小节，小节级才是可度量的。

**改法**：
- 评测集从 24 条扩到 53 条（47 可答 + 6 不可答），每条可答题加 `gold_section`（正确小节）和 `gold_points`（答案要点列表），并加 `category` 分类（basic / number / identifier / multi_hop / negative）。
- 评测指标从 `source_recall` 换成：**小节命中率@K**、**小节命中率@1**、**MRR**、**nDCG@K**、**要点覆盖率**、**拒答正确率**、**P95 检索延迟**。
- nDCG@K 采用二元相关性：命中 gold 小节记 1，`DCG = Σ rel_i / log2(i+1)`，`IDCG` 用 `min(len(gold), K)` 个 1 计算；同一小节被多个子块命中只按首次出现计一次，它是纯评估指标，不参与排序。

**代码位置**：`eval/qa_set.jsonl`（评测集）、`eval/run_eval.py`（指标计算，含 `_ndcg_at_k`）。

## 1.2 V1 → V2：父子块（small-to-big）

**现象**：600 字固定块切分，跨小节长条款被切断；检索精度和生成完整性互相打架——块大了语义被稀释，块小了答案残缺。

**原因分析**：单一块大小无法同时满足两件事：**检索要小块**（语义集中、向量不被无关文字稀释），**生成要大块**（上下文完整、答案不残缺）。这是固定块切分的结构性矛盾。

**改法**：父子块策略。
- 检索用 **110 字子块**（child，语义集中），子块带 `parent_id` 指回父块。
- 生成用**整节父块**（parent，即一个小节的完整文本），检索命中子块后「父块展开」，把整节喂给生成侧。
- 子块大小用 `eval/sweep.py` 参数扫描（见下方踩坑）。

**代码位置**：`app/splitter.py`（父块切分 + 子块切分）、`app/store.py`（父块索引 `parents` + `get_parent`）、`app/retriever.py`（父块展开 `use_parent`）、`app/generator.py`（`hit_text` 优先读父块 context）。

**实测结果**（离线模式，53 条评测集）：

| 指标 | V1 | V2 |
| --- | --- | --- |
| 小节命中率@1 | 93.6% | 89.4% |
| MRR | 0.968 | 0.941 |
| nDCG@5 | 0.976 | 0.954 |
| 要点覆盖率 | 90.0% | 87.1% |
| P95 检索 | 1.8 ms | 2.4 ms |

**踩坑（重要）**：V2 的**离线覆盖率不升反降**，一开始以为是切分 bug，逐题排查后确认——是两条「转正」相关的题目在 V1/V2 下各答对一条、各答错一条，互相抵消。根因是**离线抽取式回答的句子挑选对块边界敏感**，不是父子块本身的问题。父子块的真正价值是「喂给大模型生成的上下文更完整」，这个收益要在接真实大模型后才能通过生成质量体现；离线抽取式只能验证「父块展开链路对不对」。

## 1.3 V2 → V3：BM25 + RRF 混合召回

**现象**：纯向量检索对编号、专有名词（`HR-2024-07`、`IT 工单系统`）不敏感，容易漏。

**原因分析**：向量（尤其离线哈希向量）偏语义/字面整体相似，对「精确关键词匹配」不擅长；而制度文档里大量「表单编号」「具体数字」「专有系统名」恰恰需要精确匹配。经典的解法是「稠密向量 + 稀疏关键词」双路召回，用 RRF 融合。

**改法**：
- 纯 Python 自写 Okapi BM25（`app/bm25.py`），中文用 2-gram 分词，零第三方依赖（不引 rank_bm25 / whoosh）。
- RRF（Reciprocal Rank Fusion）融合两路名次：`score = Σ 1/(k + rank)`，避开向量分与 BM25 分不同量纲的归一化问题。

**代码位置**：`app/bm25.py`（BM25Index）、`app/retriever.py`（RRF 融合逻辑，`use_bm25` 开关）。

**实测结果**（离线模式）：

| 指标 | V2 | V3 |
| --- | --- | --- |
| 小节命中率@1 | 89.4% | 89.4% |
| MRR | 0.941 | 0.941 |
| nDCG@5 | 0.954 | 0.955 |
| 要点覆盖率 | 87.1% | 87.1% |
| P95 检索 | 2.4 ms | 2.5 ms |

**踩坑（重要，这是最诚实的结论）**：**BM25 在本语料上几乎零收益**——逐条对比 V1 vs V3 的 Top-1，47 个可答题的 Top-1 小节**一条都没变**。这不是 bug，是真实结论：**3 份文档、47 个可答题，向量检索已经能稳定命中正确小节，BM25 的稀疏召回没有额外空间**。BM25 的价值在大规模、含大量专有名词/编号/缩写、且向量（尤其离线哈希向量）覆盖不了的语料上才体现。

## 1.4 V3 → V4：规则精排（零依赖替代 cross-encoder）

**现象**：Top-K 里仍可能混入弱相关块，尤其小节标题命中时排序不够准。

**原因分析**：真正的 cross-encoder（如 bge-reranker）需要 GPU/模型，离线环境没有。但「精排」这个环节的意义——把候选重排、让最相关的小节排第一——可以用轻量规则近似。

**改法**：四路规则打分（`app/reranker.py`）：
1. **覆盖度**：问题词（去停用词后的 token）在候选文本里出现了多少；
2. **小节标题命中**：问题词在小节标题里出现了多少——制度文档的标题就是"这段在讲什么"的标签；
3. **邻近度**：问题词在文本中的**聚集程度**——同一问题的多个关键词是否挤在同一小段（滑动窗口）里，
   而不是"相邻块是否也命中"；
4. **原始名次 prior**：把 RRF 融合阶段的名次换算成 0~1 的先验，避免精排把强召回结果全部推翻。

四路加权合成精排分，重排候选取 Top-K。精排**只改顺序、不参与拒答判定**（拒答仍用向量原始分 `hit["score"]`，保证阈值不用重标）。

**代码位置**：`app/reranker.py`（Reranker）、`app/config.py`（`RERANK_*` 超参）、`app/retriever.py`（`use_rerank` 开关）。

**实测结果**（离线模式）：

| 指标 | V3 | V4 |
| --- | --- | --- |
| 小节命中率@1 | 89.4% | **100.0%** |
| MRR | 0.941 | **1.000** |
| nDCG@5 | 0.955 | **1.000** |
| 要点覆盖率 | 87.1% | **88.6%** |
| P95 检索 | 2.5 ms | 3.3 ms |

**结论**：**V4 规则精排是离线模式下真正有效的优化**——小节命中率@1 从 V1 的 93.6% 提到 100%，MRR 和 nDCG@5 都到 1.0。代价是 P95 延迟从 1.8ms 涨到 3.3ms，仍在毫秒级，可接受。

## 1.5 消融实验总表

完整四级对比（`python -m eval.ablation` 生成，写入 `eval/ablation.md`）：

| 档位 | 改动 | 小节命中率@K | 小节命中率@1 | MRR | nDCG@5 | 要点覆盖率 | 拒答正确率 | P95 检索 | 上下文均字符 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| V1 | 600 字固定块 + 纯向量 | 100.0% | 93.6% | 0.968 | 0.976 | 90.0% | 83.3% | 1.8 ms | 701 |
| V2 | 父子块（110 字子块 + 整节父块） | 100.0% | 89.4% | 0.941 | 0.954 | 87.1% | 83.3% | 2.4 ms | 761 |
| V3 | + BM25 + RRF 混合召回 | 100.0% | 89.4% | 0.941 | 0.955 | 87.1% | 83.3% | 2.5 ms | 757 |
| V4 | + 规则精排 | 100.0% | **100.0%** | **1.000** | **1.000** | **88.6%** | 83.3% | 3.3 ms | 748 |

**拒答正确率 83.3%（5/6）**：6 条不可答题里 5 条正确拒答、1 条误答。离线哈希向量的字面匹配对「库里确实没有但用词相近」的问题会误召回，这是离线模式的已知边界，接 BGE 后需重测。

> 离线模式的数字只反映**工程链路与检索策略**的相对差异；接入真实 BGE / 大模型后必须用同一脚本重跑，
> 不能把这里的绝对数值当成真实模型效果对外引用。

## 2. 数字取数口径

| 指标 | 数字 | 口径与前提 |
| --- | --- | --- |
| 小节命中率@1 | V1 93.6% → V4 100% | 离线哈希向量，53 条评测集，3 份文档；接 BGE 后重测 |
| MRR | 0.968 → 1.000 | 同上 |
| nDCG@5 | 0.976 → 1.000 | 同上；二元相关性，纯评估指标，不影响排序 |
| BM25 增量 | ≈0（小语料） | 如实写「小语料无增量，价值在大规模含编号/缩写的语料」 |
| 拒答正确率 | 83.3%（5/6） | 同上；离线字面匹配的已知边界 |

对外引用这组数字时的口径要求：
- ✅ 写清楚「离线模式 + 53 条自建评测集 + 3 份文档」；
- ✅ 可以说「规则精排使小节级命中率@1 从 93.6% 提升到 100%（离线模式）」；
- ❌ 不要写「Recall@5 提升 40%」这类没有标模式、样本量的数字。
